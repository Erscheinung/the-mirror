# CLAUDE.md

Guidance for Claude Code (and humans) working on this fork of The Mirror (Mirror Classic).

## What this fork is

A self-hosted, Firebase-free setup of Mirror Classic so a small group can build worlds together in real time over Tailscale. The original cloud (api.themirror.space, Firebase projects, prebuilt engine downloads) is shut down. Work happens on the `dev` branch of https://github.com/Erscheinung/the-mirror. The user-facing instructions are at the top of `README.md`.

## Repo layout

- `godot-engine/` is a submodule of the Mirror fork of Godot 4.3 (`the-mirror-gdp/godot`, pinned commit). It adds the `the_mirror`, `jolt` and `network_synchronizer` modules (`TMSceneSync`, `JBody3D`, `TMFileUtil`, ...). **Stock Godot 4.3/4.4/4.5 cannot run the project**, and opening it in 4.4+ rewrites project files. Build the fork with the `scripts/build-engine-*.sh`/`.ps1` scripts.
- `mirror-godot-app/` is the Godot project. It's both the game and the in-game editor, and the same binary runs as client or as a headless zone (game) server.
- `mirror-web-server/` is NestJS + MongoDB + Redis. It holds accounts, spaces, space objects and assets, and handles websockets for zone servers. It runs on Node 18–22 (Node 23+ breaks dependencies).
- `mirror-docs/` holds the upstream docs (Docusaurus). Much of it describes the defunct cloud.
- `scripts/` holds the setup and run scripts described below.

## Commands

```sh
scripts/setup-host.sh          # host: build engine + MongoDB/Redis/Node 22 + web server + .env + seed DB + import
scripts/start-server.sh        # host: run the web server on :9000 (keep running)
./setup-mac.sh | ./setup-linux.sh | setup-win.ps1   # friends: Tailscale + build tools + engine + join role + import
scripts/play.sh [--editor|--import]   # run the game / open the Godot editor (play.ps1 on Windows)
scripts/set-mirror-host.sh <ip> <host|join>   # switch role / server IP (writes mirror-godot-app/override.cfg)
scripts/seed-db.sh             # load the "Empty Space" template if the DB has no templates

# web server
cd mirror-web-server && npx yarn@1.22.22 build && npx yarn@1.22.22 test
# check the Godot project for script errors
godot-engine/bin/MirrorGodot.app/Contents/MacOS/Godot --headless --editor --quit --path mirror-godot-app
```

## How the pieces fit (self-hosted mode)

- **Auth**: `mirror-web-server/src/firebase/local-auth.service.ts` replaces Firebase unless `AUTH_PROVIDER=firebase`. Users live in the `local_auth_users` collection and tokens are HS256 JWTs signed with `LOCAL_AUTH_SECRET`. `local-auth.controller.ts` serves the Identity Toolkit / Secure Token REST paths that the Godot addon (`addons/godot-firebase`) calls. The client points there through `mirror/auth_server_url`. Errors must keep Firebase's `{error:{code,message}}` shape, which the controller-scoped filter handles.
- **Client config**: `mirror-godot-app/override.cfg` (gitignored) is copied from `addons/mirror_internal/env_configs/tailscale-{host,join}.cfg`. Godot's ConfigFile parser drops the key after a full-line `#` comment, so **use `;` for comment lines** in `.cfg` files.
- **Zone servers**: the host role (`always_spin_up_local_server=true`) spawns a headless zone server on the host's machine for the space it opens (`scripts/autoload/zone/client.gd`). The join role (`mirror/zone_server_host`) connects to that host on UDP 27015. Zone servers only decode the player JWT and don't verify it (upstream), so keep everything on the tailnet.
- **Seed data**: "Create New Space" lists spaces with `isTMTemplate: true`. `mirror-web-server/database_backup/dump.archive` provides the "Empty Space" template.
- **Assets**: `ASSET_STORAGE_DRIVER=LOCAL` stores uploads in `mirror-web-server/localStorage`, served at `ASSET_STORAGE_URL` (must be reachable by all players, so use the host's Tailscale IP).
- **Secrets**: `mirror-web-server/.env` is gitignored and generated by `setup-server.sh`. Never commit it.

## Gotchas

- macOS engine builds link MoltenVK statically (downloaded to `.engine-deps/`). Newer Homebrew requires `brew trust mongodb/brew`.
- The first `--import` after a fresh engine build can end early, so the setup scripts run it twice.
- `mirror-web-server/src/metadata.ts` is regenerated by `nest build`. If it's stale, it only disables Swagger docs.
- The Godot client still sends analytics to the original Mirror Mixpanel/PostHog projects. Blank keys trip asserts, so disabling it needs code changes.
- Linux and Windows build scripts haven't been tested on real machines yet. macOS has been verified end to end.

## Plan: always-on, async hosting (not started)

**Goal**: anyone can open any space at any time, even when the original host is offline. Several people in the same space share one live zone server.

### 1. Local zone-server launcher (needed wherever the server runs)
- The web server already asks an external "server scaler" to start zone servers (`src/zone/space-manager-external.service.ts`, `SERVER_SCALER_URL`: createContainer / status / delete). Implement a local version that spawns `Godot --headless --server --space <id> --mode edit|play --uuid <zoneId> --server_login <refresh token>` processes on the server machine.
  - Assign ports from a pool (27015+).
  - Report `ipAddress` (the server's Tailscale IP) and `port`, and set the zone state to READY once the process reports in.
  - Stop a zone server after N minutes with no players.
- The server needs a service account in `local_auth_users` for `--server_login`, and the Mirror engine build plus an imported `mirror-godot-app/` on the server machine. The editor build runs fine with `--headless` and needs no GPU. A smaller `template_release` build would need an exported `.pck` instead of the project folder.
- Client: all players use the join flow through `Net.zone_finder.join_build_server` (normal upstream path), and `always_spin_up_local_server` becomes false for everyone.
- Run the web server and the launcher as systemd services (or docker compose) so they survive reboots.

### 2. Where to run it

Estimated sizing: MongoDB + Redis + web server take about 1 GB RAM, and each active zone server takes about 300–600 MB RAM and one CPU core while in use. 2 vCPU / 4 GB covers a few friends with 1–2 active spaces. Prices below are rough; check current pricing before choosing.

| Option | Region / latency from India | Rough cost | Notes |
| --- | --- | --- | --- |
| Spare PC / Raspberry Pi 5 (8 GB) at home | local | electricity | Pi needs a `linuxbsd arch=arm64` engine build. Home uptime/power dependent. |
| DigitalOcean droplet 2 vCPU / 4 GB | Bangalore (BLR1), low latency | ~$24/mo | Simple. 1–2 GB droplets (~$6–12) work for 1 active space. |
| Hetzner CX22 / CAX21 (4 GB / 8 GB) | Singapore, ~60–90 ms | ~€4–8/mo | Cheapest per GB. CAX is ARM, so it needs an arm64 engine build. |
| AWS Lightsail 2 GB / 4 GB | ap-south-1 (Mumbai) | ~$12 / $24 per mo | Fixed price, includes transfer. Easiest AWS entry. |
| AWS EC2 t3a.medium (2 vCPU / 4 GB, x86) | ap-south-1 | ~$25–30/mo on-demand, less with Savings Plan / spot | x86 means the existing Linux build script works as is. Add a gp3 EBS volume for Mongo and assets. |
| AWS EC2 t4g.medium (Graviton ARM) | ap-south-1 | ~20% cheaper than t3a | Needs an arm64 engine build. The free-tier t4g.small trial may cover a small setup. |

### 3. AWS (ap-south-1) ideas
- Start with a **single EC2 or Lightsail instance** running everything (docker compose: mongo, redis, web server, zone launcher). Tailscale runs on the instance. Open **no public ports**; security group egress only, and players connect over the tailnet.
- **Storage**: gp3 EBS for MongoDB and `localStorage`. Do nightly `mongodump` and `tar` of `localStorage` to S3 (lifecycle to Glacier), or use EBS snapshots through Data Lifecycle Manager.
- **Cost control**: an instance scheduler (EventBridge + Lambda) to stop the instance overnight, or a Savings Plan once usage is steady. Auto-stop zone servers when spaces are empty.
- **Later, if it grows**: MongoDB Atlas (Mumbai) or DocumentDB (check compatibility) in place of self-hosted Mongo. ElastiCache for Redis. Zone servers on ECS/Fargate or an EC2 Auto Scaling group, with the launcher calling the ECS API (closer to how the original cloud worked). Asset storage on S3 would need an S3 driver; the web server only has `LOCAL` and `GCP` today.
- Keep the server on the tailnet. It has no rate limiting and zone servers don't verify tokens, so it's not ready to face the public internet.

### 4. Migration from the laptop host
1. On the new server run `scripts/setup-host.sh` (or its docker equivalent).
2. Copy the data: `mongodump` on the old host, then `mongorestore` on the new one, and copy `mirror-web-server/localStorage/`.
3. Keep the same `LOCAL_AUTH_SECRET` so existing logins keep working.
4. Update `ASSET_STORAGE_URL`, run `scripts/set-mirror-host.sh <new-ip> join` for everyone, and commit the updated `tailscale-*.cfg`.
